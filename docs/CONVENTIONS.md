# 项目约定（CONVENTIONS）

> **状态：草案**，待确认。这些是"写代码之前先说好的事"。
> 约定存在的意义是：让三个月后的人（包括失忆的 AI）能看懂这个项目，
> 而不用去猜。

---

## 1. 语言与依赖

- Python 3.12+（见 ADR-0002）
- **运行时零第三方依赖**。想加依赖必须先问，并且说清标准库为什么不够
- 开发期也不引入测试框架，用标准库 `unittest`
- 不引入任何会自行联网的依赖

## 2. 目录结构

采用 `src` 布局，源码与测试分离：

```
homecheck/
├── docs/                  # 所有文档（本项目的事实来源）
│   ├── PRODUCT.md         # 做什么 / 不做什么
│   ├── DECISIONS.md       # 决策记录
│   ├── CONVENTIONS.md     # 本文件
│   └── TASKS.md           # 待办与进度（S1 开始时创建）
├── src/homecheck/         # 源码
│   ├── __init__.py
│   ├── cli.py             # 命令行入口与参数解析（只做解析和分发）
│   ├── scan.py            # 扫描与统计（只读）
│   ├── report.py          # 输出格式化（终端 / JSON / Markdown）
│   ├── suggest.py         # 建议引擎（只产出建议，无副作用）
│   └── apply.py           # 执行改动（唯一允许写文件系统的模块）
├── tests/                 # 测试，与源码一一对应
├── README.md
└── pyproject.toml
```

**关键约束**：`apply.py` 是**唯一**允许改动文件系统的模块。
`scan.py` / `report.py` / `suggest.py` 必须保持只读，且这一条要能被测试验证。

## 3. 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 模块 / 函数 / 变量 | `snake_case` | `scan_directory`, `total_size` |
| 类 | `PascalCase` | `ScanResult` |
| 常量 | `UPPER_SNAKE_CASE` | `DEFAULT_MAX_FILE_SIZE` |
| 私有成员 | 前缀 `_` | `_walk_entries` |
| 布尔值 / 判断函数 | `is_` / `has_` / `should_` 前缀 | `is_duplicate`, `has_permission` |
| 测试文件 | `tests/test_<模块>.py` | `tests/test_scan.py` |
| 测试函数 | `test_<被测行为>_<条件>` | `test_detect_duplicates_ignores_empty_files` |

## 4. 代码风格

- 遵循 PEP 8，4 空格缩进，行长上限 100
- **所有函数必须有类型注解**（参数与返回值）
- 公开函数和类必须有 docstring，说明：做什么、参数含义、返回什么、可能抛什么异常
- 不写"废话注释"（`# 增加计数` 这种）。注释只解释**为什么**，不解释**是什么**
- 不用 `print` 做调试残留。真正的输出走统一的输出层

## 5. 错误处理

- **禁止裸 `except:`**，也禁止 `except Exception: pass`
- 权限错误（`PermissionError`）必须捕获，并**记录下具体路径**，不能静默跳过
- 单个文件出错不能让整个扫描崩掉 —— 记录后继续
- 异常信息要给用户能理解的话，不是原始 traceback 直接糊脸

## 6. 安全红线

这几条和 `PRODUCT.md` 的非目标直接对应，属于**不可协商**：

1. **默认零写入**：不传 `--apply` 时，进程不得对文件系统产生任何修改
2. **`apply.py` 之外禁止写文件** —— 包括创建临时文件、缓存文件
3. **测试绝不触碰真实文件系统**：一律在 `tempfile` 临时目录里造夹具
4. **测试绝不真的删除用户文件**，只操作自己创建的临时数据
5. **破坏性操作必须先 dry-run**，并打印将要发生什么，等确认

## 7. 输出约定

- 人类可读信息走 `stdout`；警告与错误走 `stderr`
- `--json` 模式下 **stdout 只输出 JSON**，不含任何装饰性文字（保证可被管道消费）
- JSON 字段名一旦发布即视为**破坏性接口**，改名必须记录进 `DECISIONS.md`
- 终端输出不依赖颜色传达关键信息（管道 / 重定向后颜色会丢失）

## 8. 提交规范

采用 Conventional Commits：

```
feat: 增加重复文件检测（S2）
fix: 修正符号链接导致的重复计数
docs: 补充 Q5 的清理策略说明
test: 补齐空文件的边界用例
refactor: 抽出体积统计为独立函数
chore: 初始化仓库
```

- **每个切片至少一次提交**，且提交时测试必须是绿的
- 提交信息说明**为什么**，不只是"改了什么"
- 切片的验收未通过前，不提交

## 9. 文档约定

- 所有决策写进 `docs/DECISIONS.md`，**不要埋在代码注释里**
- `docs/` 是项目的事实来源。代码与文档冲突时，**先改文档再改代码**
- 每完成一个切片，更新 `docs/TASKS.md` 的进度

## 10. 人机协作约定

> 这一节约束的是 AI 助手的行为，防止范围蔓延。

**任务发起模板**（由项目所有者填写）：

```
目标：这一步要达成什么
范围：只允许改 <哪些文件/目录>
验收：怎么算做完
约束：不要动 <什么>
```

**AI 的响应模板**：

```
理解：复述一遍需求（供纠正）
计划：分几步，每步产出什么
改动：预计动哪些文件
需要你决定：×××（不自行拍板的部分）
```

**AI 的硬性行为边界**：

1. 只改任务声明的范围内文件，越界前必须先问
2. 先读后改；改动尽量小、可读、可回滚
3. 需求有歧义时**停下来问**，不许自行脑补
4. 交付时如实报告：改了什么、没改什么、有什么风险
5. 不做任何"顺手"的事（格式化、重构、升级依赖）
6. 未获批准不执行 `git init` / 提交 / 删除 / 移动等有副作用的操作
